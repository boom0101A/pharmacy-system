# نظام إدارة الصيدلية

نظام سطح مكتب لإدارة صيدلية واحدة على عدة أجهزة ضمن شبكة محلية، بدون انترنت.

- **الخادم** (`apps/server`) — Node.js + Express + Prisma + PostgreSQL
- **العميل** (`apps/desktop`) — Electron + React + CSS Modules + Radix UI
- **الأنواع المشتركة** (`packages/shared-types`)

> **البيع نقداً فقط.** لا يوجد بيع بالآجل ولا ديون ولا أقساط في هذا النظام — لا في قاعدة البيانات ولا في الواجهة.

---

## المتطلبات

- Node.js 20 أو أحدث
- PostgreSQL 14 أو أحدث (على الجهاز الذي سيعمل كخادم)

## التشغيل أول مرة

```bash
npm install

# 1) إعداد الاتصال بقاعدة البيانات
cp apps/server/.env.example apps/server/.env
#    عدّل DATABASE_URL و JWT_SECRET داخل الملف.
#    الخادم يرفض الإقلاع إذا بقي JWT_SECRET بقيمته الافتراضية أو كان أقصر من 32 حرفاً.
#    لتوليد قيمة صالحة:
#      node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

# 2) إنشاء الجداول + بيانات تجريبية
npm run db:migrate --workspace=@pharmacy/server
npm run db:seed    --workspace=@pharmacy/server

# 3) تشغيل الخادم
npm run dev:server

# 4) تشغيل التطبيق (في طرفية أخرى)
npm run dev:desktop
```

حساب الدخول بعد الـ seed: `admin` / `admin123` (ويوجد أيضاً `cashier` / `cashier123`).

## التشغيل على عدة أجهزة

1. شغّل PostgreSQL والخادم على جهاز واحد يبقى يعمل طوال الدوام.
2. ثبّت IP محلي ثابت لذلك الجهاز من إعدادات الراوتر.
3. على كل جهاز آخر، افتح التطبيق واكتب عنوان الخادم في شاشة الدخول أو في الإعدادات، مثل `http://192.168.1.10:3000`.

## التسليم عند العميل

### الطريقة المعتمدة: مثبّت واحد شامل

```bash
npm run build --workspace=@pharmacy/desktop
# الناتج: apps/desktop/release/pharmacy-system-setup-<version>.exe  (~147 ميجا)
```

هذا الملف وحده كافٍ. يحمل داخله **PostgreSQL مقلَّماً (نسخة ويندوز x64) والخادم كاملاً**، فلا يحتاج العميل تثبيت قاعدة بيانات ولا Node.js ولا أي إعداد يدوي:

1. أول تشغيل ينشئ قاعدة بيانات خاصة بالجهاز داخل مجلد بيانات المستخدم، يطبّق الترحيلات، ويبذر حسابي `admin`/`cashier` — يستغرق نحو ١٠-٢٠ ثانية تظهر خلالها رسالة "جارٍ تهيئة قاعدة البيانات لأول مرة…".
2. كل تشغيل لاحق يقلع خلال ثوانٍ.
3. كل ما يُكتب (قاعدة البيانات، الصور، النسخ الاحتياطية، السجلات) يعيش في `%APPDATA%` لا في مجلد التثبيت، فلا يتأثر بصلاحيات `Program Files` ولا يُمسح عند إزالة التطبيق.
4. **أجهزة كاشير إضافية**: ثبّت نفس الملف عندها، ثم في "الإعدادات ← عنوان الخادم" اكتب عنوان الجهاز الرئيسي (يعرضه الجهاز الرئيسي نفسه أسفل نفس الحقل، مثل `http://192.168.1.10:3000`). عندها يتوقف الجهاز الثاني عن تشغيل خادمه المدمج ويعتمد على الأول.

**قيد يجب إبلاغ العميل به**: الخادم يعمل داخل التطبيق على الجهاز الرئيسي، فإغلاق التطبيق هناك يقطع الخدمة عن بقية الأجهزة. لصيدلية بجهاز واحد لا أثر لهذا. لتشغيل الخادم مستقلاً عن التطبيق، استخدم طريقة الخدمة أدناه.

إن تعذّر الإقلاع عند العميل، ملف `%APPDATA%\@pharmacy\desktop\logs\bootstrap.log` يحوي سبب الفشل بالضبط.

### بديل: الخادم كخدمة ويندوز

في وضع التطوير يعمل الخادم بأمر يدوي في طرفية مفتوحة — وهذا لا يصلح عند عميل: إعادة تشغيل الجهاز تُوقف النظام بالكامل حتى يأتي من يشغّله. الحل تثبيته كخدمة ويندوز حقيقية تُقلع تلقائياً وتعيد تشغيل نفسها عند التعطّل.

```bash
# 1) بناء نسخة الإنتاج
npm run build --workspace=@pharmacy/server

# 2) حمّل nssm.exe من https://nssm.cc (ملف تنفيذي مستقل، ليس حزمة npm)

# 3) من PowerShell "كمسؤول":
cd apps/server
powershell -ExecutionPolicy Bypass -File .\scripts\install-service.ps1 -NssmPath C:\nssm\nssm.exe
```

السكربت يتحقق من وجود `.env` ومن نسخة الإنتاج قبل التثبيت، ويضبط `AppDirectory` على مجلد الخادم — بدونها تعمل الخدمة من `System32` فلا يجد `dotenv` ملف `.env` ويموت الخادم عند كل إقلاع.

**التحقق:** أعد تشغيل الجهاز، ثم افتح من جهاز آخر على الشبكة `http://<ip-الخادم>:3000/api/health` دون تسجيل دخول على جهاز الخادم.

الأعطال تُسجَّل في `apps/server/logs/server.log` (بصيغة JSON lines، تُدوَّر عند 5 ميغابايت)، ومخرجات الخدمة نفسها في `logs/service-out.log` و`logs/service-err.log`.

### أيقونة المثبّت

`apps/desktop/build/icon.ico` موجود حالياً بأيقونة **مؤقتة** (صليب طبي أبيض على مربّع أخضر متدرّج بألوان الهوية). لاستبدالها بشعار الصيدلية الحقيقي: ضع الشعار بصيغة PNG مربّعة (512×512 أو أكبر) مكان `apps/desktop/build/icon-source.png` ثم:

```bash
npm run build:icon --workspace=@pharmacy/desktop
```

لا يحتاج الأمر أي تعديل في الكود — السكربت يعيد توليد `icon.ico` من ملف المصدر.

## النسخ الاحتياطي والاستعادة

يُصدَّر كامل محتوى قاعدة البيانات إلى ملف JSON عند تشغيل الخادم ثم كل 24 ساعة، داخل `BACKUP_DIR` مع الاحتفاظ بآخر `BACKUP_RETENTION` نسخة. **اضبط `BACKUP_DIR` على قرص خارجي** — نسخة احتياطية على نفس القرص لا تنفع إذا تلف القرص.

### الاستعادة

الاستعادة **تمسح كل البيانات الحالية** وتستبدلها بمحتوى الملف. لذلك هي سكربت يُشغَّل على جهاز الخادم نفسه، وليست زراً داخل التطبيق: أي حساب مدير مخترَق على أي جهاز كاشير كان سيصبح قادراً على مسح بيانات الصيدلية عن بُعد بضغطة زر.

```bash
# أوقف الخدمة أولاً
nssm stop PharmacyServer

cd apps/server
npm run db:restore                       # يعرض النسخ المتاحة
npm run db:restore -- backup-2026-09-08T03-00-00.000Z.json
```

السكربت يطبع اسم قاعدة البيانات الهدف وتاريخ النسخة، ويطلب كتابة `RESTORE` حرفياً للمتابعة (أي إدخال آخر يُلغي العملية، والتشغيل غير التفاعلي يُلغى تلقائياً)، ثم **يأخذ نسخة أمان للوضع الحالي قبل المسح**. كل شيء يجري داخل transaction واحدة: إن فشلت الاستعادة في منتصفها تبقى البيانات كما كانت بدل أن تُترك ممسوحة نصفياً.

## الاختبارات

اختبارات الخادم تعمل بـ Vitest على **قاعدة بيانات منفصلة عن قاعدة التطوير**، حتى لا تُمسح أو تتلوّث بياناتك الحقيقية.

```bash
# مرة واحدة فقط: إنشاء قاعدة الاختبار وتطبيق الجداول الموجودة عليها
# (migrate deploy فقط يطبّق migrations جاهزة، لا يُنشئ جديدة ولا يطلب تأكيداً تفاعلياً)
createdb pharmacy_test
cd apps/server
DATABASE_URL="postgresql://postgres:postgres@localhost:5432/pharmacy_test?schema=public" \
  npx prisma migrate deploy

cd ../..

# تأكد من ضبط DATABASE_URL_TEST في apps/server/.env (راجع .env.example)

# تشغيل الاختبارات
npm test --workspace=@pharmacy/server
```

## ملاحظات معمارية

**الدفعات و FEFO.** الكمية لا تُخزَّن على الصنف مباشرة، بل على **دفعات** لكل منها تاريخ انتهاء خاص. عند البيع يسحب النظام من الدفعة الأقرب انتهاءً أولاً، وقد يمتد سطر واحد في الفاتورة على أكثر من دفعة. المنطق كله في [sales.service.ts](apps/server/src/services/sales.service.ts).

**البيع المتزامن.** عملية البيع تجري داخل transaction واحدة مع `SELECT … FOR UPDATE` على دفعات الصنف، حتى لا ينجح كاشيران في بيع آخر علبة بنفس اللحظة. هذا هو سبب اختيار PostgreSQL بدل SQLite.

**تكرار الفواتير.** إذا انقطع الاتصال بعد أن سجّل الخادم البيع لكن قبل وصول الرد، يرى الكاشير فشلاً وتبقى السلة — وإعادة المحاولة كانت ستُنشئ فاتورة ثانية وتخصم المخزون مرتين. لذلك ترسل الواجهة `idempotencyKey` ثابتاً لكل محاولة بيع (يتغيّر فقط عند نجاح البيع أو تعديل السلة)، والخادم يُعيد الفاتورة الأصلية بدل إنشاء واحدة جديدة. العمود فريد في قاعدة البيانات، فحتى طلبان متزامنان تماماً لا ينتج عنهما إلا فاتورة واحدة.

**الصلاحيات.** تُفرض في الخادم عبر `checkRole` على مستوى المسار ([auth.ts](apps/server/src/middleware/auth.ts))، وليس بإخفاء الأزرار فقط — إخفاء الزر لا يمنع طلباً مباشراً على الـ endpoint. الواجهة تخفي ما سيرفضه الخادم أصلاً.

**التنسيق.** كل الألوان والمسافات والخطوط معرَّفة كـ CSS custom properties في [tokens.css](apps/desktop/src/renderer/styles/tokens.css)، وكل مكوّن له ملف `.module.css` خاص به. اللوحة خضراء/زرقاء طبية ولا تحتوي أي لون بنفسجي. مكوّنات Radix تُستخدم للسلوك وإمكانية الوصول (Dialog, Toast, Label) والتنسيق كله من عندنا.

**الحركة.** مدد الحركة ومنحنياتها توكنات في [tokens.css](apps/desktop/src/renderer/styles/tokens.css)، ولا توجد مكتبة انميشن — كل شيء `@keyframes` في ملف `.module.css` الخاص بالمكوّن. نفس الملف يحتوي تعطيلاً عاماً لـ `prefers-reduced-motion` يغطي أي `animation`/`transition` تلقائياً، **لكنه لا يغطي أمرين**: مؤقتات JavaScript (مثل مدة الشاشة الترحيبية، لذلك يفحص [Splash.tsx](apps/desktop/src/renderer/components/Splash.tsx) الإعداد بنفسه عبر `matchMedia`)، و`animation-delay` (يُصفَّر يدوياً حيث استُخدم).

**الخطوط.** يجب استضافة الخطوط محلياً — النظام يعمل بدون انترنت، فأي `@import` من Google Fonts سيفشل بصمت. التفاصيل في [global.css](apps/desktop/src/renderer/styles/global.css).

## اختصارات لوحة المفاتيح

الصيدلية تعمل على لوحة المفاتيح لا الماوس، خصوصاً خلف الكاونتر.

| المفتاح | أين | ماذا يفعل |
|---|---|---|
| `F12` | نقطة البيع | إتمام البيع |
| `F4` | نقطة البيع | الانتقال لحقل الخصم |
| `↑` / `↓` | نقطة البيع (والمؤشر في حقل البحث) | التنقّل بين نتائج البحث |
| `Enter` | نقطة البيع | إضافة الصنف المحدَّد للسلة (أو البحث بالباركود إن لم يكن هناك تحديد) |
| `Esc` | نقطة البيع | إلغاء التحديد، وبضغطة ثانية تفريغ السلة |
| `↑` / `↓` | الشريط الجانبي (بعد الوصول إليه بـ`Tab`) | التنقّل بين الأقسام |
| `F1` | المخزون | فتح نموذج "دواء جديد" |
| `F2` | نموذج الدواء | حفظ الدواء |

الأسهم في نقطة البيع تعمل **فقط** والمؤشر في حقل البحث/الباركود — في أي مكان آخر تبقى للعنصر المحدَّد نفسه، فحقول الكميات في السلة تظل تزيد وتنقص بالأسهم كالمعتاد.

## ما لم يُنفَّذ عمداً

**البيع أثناء انقطاع الشبكة.** لا توجد طوابير بيع تعمل بلا اتصال. سبب ذلك أن البيع يعتمد على `SELECT … FOR UPDATE` داخل transaction على الخادم لمنع بيع آخر علبة مرتين؛ أي طابور محلي يعني اتخاذ قرار المخزون على جهاز لا يعرف ما باعته الأجهزة الأخرى. بدلاً من ذلك يظهر شريط تنبيه فور انقطاع الاتصال (استطلاع `/api/health` كل 7 ثوانٍ)، ويُعطَّل زر إتمام البيع، وتبقى السلة كما هي لإعادة المحاولة عند عودة الاتصال.

**تقرير أداء الكاشير.** لا يوجد في قاعدة البيانات مفهوم وردية (وقت دخول/خروج)، فأي تقرير "لكل وردية" سيكون في الحقيقة تجميعاً يومياً لكل كاشير ويُقدّم صورة أدق مما يملكه النظام فعلاً. مؤجَّل حتى تُضاف الورديات كميزة قائمة بذاتها.
